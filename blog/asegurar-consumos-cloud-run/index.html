Cloud Run: Cómo asegurar consumos y evitar facturas sorpresa

Desplegar un contenedor en Cloud Run es fácil. Optimizar su costo exige entender la concurrencia y los modelos de facturación. Así aseguras tus consumos.

Has desplegado tu flamante microservicio en Cloud Run. Responde en milisegundos, escala automáticamente si el tráfico sube, y no tienes que pensar en parches del sistema operativo. La magia del serverless funciona perfecto.

Pero a fin de mes llega la factura y los números no encajan. Pensaste que estabas pagando solo por uso, y sin embargo, el costo de CPU y RAM está disparado para el nivel de tráfico real de tu aplicación.

El problema de Cloud Run es que la configuración por defecto es asombrosamente buena para arrancar y pésima para optimizar costos en flujos de trabajo específicos. Si quieres asegurar tus consumos, hay tres palancas que tienes que mover.

El problema real: CPU asignada vs CPU cobrada

El comportamiento predeterminado de Cloud Run es la facturación por petición (request-based billing). Funciona de esta forma: solo pagas por la CPU y la RAM de una instancia durante el tiempo exacto que esté procesando al menos una solicitud activa. Si la instancia está inactiva (ociosa) esperando tráfico, no te cobran.

Sin embargo, hay una trampa sutil. Cuando Cloud Run escala bajo presión, lanza nuevas instancias, las cuales tardan un instante en arrancar (el famoso cold start). Para minimizar este impacto, Cloud Run mantiene algunas instancias “calientes” en segundo plano. Aunque no te cobran por esas instancias ociosas en el modelo por petición, si decides usar variables globales para mantener conexiones vivas a la base de datos o ejecutas tareas en segundo plano usando goroutines o hilos sueltos, esa CPU se “apaga” cuando no hay solicitudes HTTP entrantes.

Si habilitas la facturación por instancia (asignando la CPU siempre encendida, CPU always allocated), la CPU nunca se acelera en vacío. Tu código de fondo sigue corriendo. El problema es que ahora te cobran por cada milisegundo de vida del contenedor, tenga peticiones o no, hasta que se apague por inactividad prolongada (a los 15 minutos). Y eso, si tienes un mínimo de instancias configurado (min-instances), garantiza una factura abultada 24/7.

Cómo funciona la concurrencia (tu mejor amigo financiero)

A diferencia de AWS Lambda, que ejecuta una solicitud por instancia a la vez, Cloud Run es un animal multihilo. Puede manejar múltiples solicitudes concurrentes en el mismo contenedor.

Por defecto, la concurrencia máxima (--concurrency) es 80. Esto significa que Cloud Run no arrancará una segunda instancia hasta que la primera reciba su petición número 81 al mismo tiempo.

Si tu aplicación en Node.js, Go o Java es asíncrona y eficiente, subir la concurrencia a 250 o 500 reduce radicalmente el número de instancias necesarias y, por lo tanto, reduce el costo total. En la factura, esto se traduce en una utilización altísima de los recursos por los que ya estás pagando.

Manos a la obra: Optimizando la configuración

Veamos cómo ajustar esto usando gcloud. Imagina que tenemos un servicio en Go, que es extremadamente eficiente pero requiere mantener un pool de conexiones a la base de datos en segundo plano.

Primero, si el servicio hace trabajo de fondo asíncrono y necesitamos CPU always allocated, ajustamos el comando de despliegue. Y para que no nos quiebre, debemos asegurarnos de que escale a cero y tenga un max-instances estricto.

gcloud run deploy mi-api \
  --image us-central1-docker.pkg.dev/PROJECT_ID/mi-repo/mi-imagen:v2 \
  --region us-central1 \
  --no-cpu-throttling \
  --min-instances 0 \
  --max-instances 5 \
  --concurrency 150 \
  --cpu 1 \
  --memory 512Mi

Con --no-cpu-throttling (facturación por instancia), la CPU siempre está activa. La clave financiera aquí es --min-instances 0 y --max-instances 5. Nunca pagaremos por más de 5 instancias completas, y si el tráfico desaparece, el costo cae a cero tras el periodo de enfriamiento.

Cuándo NO usar CPU siempre activa

Si tu servicio responde a una petición HTTP y termina su ciclo de trabajo ahí mismo (un CRUD estándar, un webhook sin procesamiento asíncrono pesado), mantener la CPU asignada te hará perder dinero, incluso con la concurrencia alta.

En esos casos, debes usar --cpu-throttling (facturación por petición). Te garantiza que solo los milisegundos útiles de CPU sean facturados. Y si sufres por los arranques en frío, una mejor solución es usar lenguajes compilados (Go, Rust), optimizar dependencias (Node.js sin frameworks pesados), o habilitar los arranques acelerados por CPU (CPU boost) de Cloud Run, que te da más potencia gratis solo durante el arranque.

Llévatelo

Para asegurar los consumos y evitar facturas sorpresa:

  1. Revisa el tipo de carga: Usa facturación por petición (throttling) para APIs puras que mueren al responder. Usa facturación por instancia (no-throttling) si haces trabajo en hilos en segundo plano, pero amárralo con max-instances.
  2. Sube la concurrencia: Si tu framework lo permite, salir del valor 80 y subirlo a 200 reduce drásticamente los arranques en frío y las instancias totales facturadas.
  3. Mide tu RAM: A diferencia de otros servicios serverless, en Cloud Run puedes asignar CPU y RAM de forma independiente. No pagues por 1GB si tu microservicio consume 120MB en el pico. Ajusta los límites.
