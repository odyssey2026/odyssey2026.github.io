Cloud Run o GKE Autopilot: cómo elegir sin arrepentirte

La decisión real entre Cloud Run y GKE Autopilot no es de rendimiento, es de control versus simplicidad operativa. Cuándo usar cuál y por qué.

Llegas al momento del diseño de arquitectura para tu nuevo microservicio. Quieres contenedores (porque ya no estamos en 2012) y no quieres administrar nodos (porque tienes cosas mejores que hacer con tu vida). Google Cloud te pone dos opciones sobre la mesa: Cloud Run y GKE Autopilot.

A simple vista, ambos prometen olvidarte de la infraestructura. Sin embargo, elegir el equivocado puede llevarte a una complejidad innecesaria o a un callejón de limitaciones. La decisión real se reduce a una sola variable: control del ecosistema versus simplicidad operativa.

El problema real de los contenedores

Empaquetar código en un contenedor es fácil. Lo difícil viene al segundo siguiente: ¿cómo lo exponemos a internet con HTTPS? ¿Cómo escalamos de 0 a 100 instancias en segundos? ¿Quién gestiona certificados, enrutamiento de tráfico y la infraestructura subyacente?

Kubernetes tradicional (GKE Standard) te da todas las herramientas para resolverlo, pero a cambio te pide administrar grupos de nodos, planificar actualizaciones y mantener una cantidad generosa de YAML.

Cloud Run y GKE Autopilot existen para quitarte ese peso de encima, pero lo hacen desde filosofías distintas: uno esconde Kubernetes por completo; el otro te lo entrega gestionado.

Cómo funciona cada modelo

Cloud Run es la definición de “tráeme un contenedor y yo me encargo del resto”. Hoy ofrece tres formas de ejecutar código: services (responden a peticiones HTTP y eventos con una URL https propia), jobs (tareas que se ejecutan hasta terminar) y worker pools (cargas en segundo plano que consumen de colas como Pub/Sub o Kafka, sin endpoint HTTP). Escala a cero cuando no hay trabajo y no expone la API de Kubernetes.

GKE Autopilot, por otro lado, sigue siendo Kubernetes. Tienes la API completa, usas kubectl, instalas Helm charts y defines Deployments. La diferencia frente a GKE Standard es que Google administra los nodos, el escalado y la seguridad base del clúster por ti.

La regla de oro del punto de partida

Cloud Run debería ser tu punto de partida por defecto para cargas sin estado (stateless). Si tu aplicación recibe una petición, procesa algo, guarda el resultado en una base de datos y responde, Cloud Run es la herramienta exacta.

GKE Autopilot se justifica cuando necesitas algo que el modelo de Cloud Run no ofrece, y casi siempre ese “algo” es el ecosistema de Kubernetes.

Manos a la obra: desplegando en la vida real

Veamos la diferencia en la experiencia del desarrollador. Para desplegar un service en Cloud Run, literalmente necesitas un comando. Google Cloud crea el endpoint HTTPS con su certificado y configura el autoescalado basado en concurrencia: cada instancia puede atender hasta 1000 peticiones simultáneas (el valor por defecto es 80, y lo ajustas según tu aplicación).

gcloud run deploy mi-servicio \
  --image us-central1-docker.pkg.dev/PROJECT_ID/mi-repo/mi-imagen:v1 \
  --region us-central1 \
  --allow-unauthenticated

Fíjate en la ruta de la imagen: usa Artifact Registry (*-docker.pkg.dev). Container Registry (gcr.io) dejó de aceptar nuevas imágenes en marzo de 2025, así que muchos tutoriales antiguos ya no funcionan tal cual. Y solo usa --allow-unauthenticated si el servicio debe ser realmente público.

Para hacer lo equivalente en GKE Autopilot, necesitas:

  1. Crear el clúster (toma varios minutos).
  2. Escribir un Deployment.
  3. Exponerlo con un Service de tipo LoadBalancer o con Gateway/Ingress.
  4. Configurar certificados gestionados para HTTPS.

Cloud Run gana con claridad en fricción inicial.

Cuándo NO usar Cloud Run (y saltar a Autopilot)

Cloud Run ha crecido mucho: sidecars, montaje de volúmenes (Cloud Storage y NFS), GPUs y worker pools para trabajo sin HTTP. Aun así, hay escenarios donde el modelo se queda corto:

  1. El ecosistema de Kubernetes es obligatorio: dependes de operadores (por ejemplo, Prometheus Operator o cert-manager), de Custom Resource Definitions o de Helm charts que esperan un clúster completo.
  2. Patrones de red avanzados: necesitas exponer protocolos arbitrarios TCP/UDP hacia afuera, service mesh con control fino o comunicación directa entre Pods.
  3. Cargas con estado de verdad: requieres StatefulSets con volúmenes persistentes ligados a cada réplica.
  4. Agentes por nodo: ejecutar DaemonSets de observabilidad o seguridad (Autopilot los permite, con restricciones).

Costos, límites y errores comunes

El modelo de facturación difiere de raíz, según la documentación pública consultada:

Modelo Facturación Lo mejor para…
Cloud Run Por recursos usados. Con facturación por petición (predeterminada) pagas solo mientras la instancia procesa peticiones; con facturación por instancia pagas todo su ciclo de vida, útil para trabajo en segundo plano. Tráfico con picos, APIs, sitios web, eventos esporádicos.
GKE Autopilot Tarifa de gestión por clúster (con crédito gratuito mensual por cuenta de facturación) más los recursos que solicitan tus Pods, exista tráfico o no. Si exiges hardware específico (GPU o una serie de máquina concreta), pasa a facturación por nodo. Tráfico sostenido, cargas base predecibles, plataformas con muchos microservicios.

El error más común: empezar con GKE Autopilot “por si algún día necesitamos Kubernetes”. Mover un contenedor estándar de Cloud Run a Kubernetes más adelante es un trabajo acotado (manifiestos, red, identidades), mientras que operar un clúster desde el día uno tiene un costo diario en actualizaciones, RBAC y revisión de manifiestos.

El segundo error: sobredimensionar los requests en Autopilot. Como pagas por lo que solicitas, un Pod que pide 4 vCPU y usa 0,3 te cuesta 4.

Llévatelo

  • Empieza con Cloud Run: si tu app procesa HTTP, eventos o colas y no guarda estado local, te ahorrarás semanas de infraestructura.
  • Evalúa el ecosistema: si necesitas Helm, CRDs, operadores o red de bajo nivel, ve por GKE Autopilot.
  • Mira tu curva de tráfico: para cargas variables con tiempos muertos, Cloud Run suele ganar; para cargas constantes 24/7, compara con Autopilot usando la calculadora oficial antes de decidir.
  • Revisa tus rutas de imagen: si todavía ves gcr.io en tus pipelines, migra a Artifact Registry.
