Cloud Run y tu VPC: Direct VPC egress o conectores

Descubre cómo conectar Cloud Run a recursos privados en tu VPC. Analizamos diferencias entre Direct VPC egress y el Serverless VPC Access connector.

Imagina que acabas de desplegar tu flamante aplicación en Cloud Run. Todo funciona perfecto hasta que necesitas que esa app hable con una base de datos Cloud SQL con IP privada o un clúster de Redis. De repente, tu código serverless choca contra un muro: por defecto, Cloud Run vive en una red administrada por Google, separada de tu Virtual Private Cloud (VPC).

Conectar Cloud Run a tus recursos privados es una travesía obligatoria para casi cualquier arquitectura de producción. La buena noticia es que tienes opciones. La noticia no tan buena es que elegir mal puede costarte caro en latencia, dinero o dolores de cabeza operativos. Hoy, nos sumergimos en las dos formas de cruzar este puente: el clásico Serverless VPC Access connector y el más moderno Direct VPC egress.

El problema real

El entorno serverless es hermoso porque abstrae la infraestructura. Pero esa misma abstracción significa que tus contenedores se ejecutan fuera de tu VPC.

Si tu base de datos o API interna solo tiene una IP privada (como debería ser en producción por seguridad), Cloud Run no puede alcanzarla mágicamente. Necesitas una tubería que conecte ambos mundos. Sin esta conexión, los tiempos de espera (timeouts) en tu aplicación empezarán a multiplicarse y la experiencia del usuario se hundirá como una piedra.

Hasta hace poco, la única tubería disponible era el Serverless VPC Access connector, un recurso adicional que tenías que aprovisionar y gestionar. Luego, Google introdujo Direct VPC egress, prometiendo una experiencia verdaderamente serverless. Pero, ¿son intercambiables? No exactamente.

Cómo funciona

Veamos las entrañas de cada enfoque para entender qué está pasando realmente bajo el capó.

El enfoque tradicional: Serverless VPC Access Connector

El Serverless VPC Access connector no es magia. Bajo la superficie, es un grupo de instancias de Compute Engine (VMs) gestionadas que Google aprovisiona en tu proyecto y conecta a una subred de tu elección.

Cuando tu servicio de Cloud Run hace una petición a una IP interna, el tráfico sale del entorno de Cloud Run, atraviesa estas instancias intermedias (el conector) y finalmente llega a tu VPC.

Esto trae consigo las limitaciones del hardware subyacente. Un conector basado en máquinas e2-micro, por ejemplo, tiene un ancho de banda estimado de entre 200 y 1000 Mbps. Si tu aplicación necesita más potencia, tienes que escalar el conector añadiendo más instancias o usando tipos de máquina más grandes (como e2-standard-4). Esto significa que vuelves a pensar en servidores, rompiendo parcialmente la promesa serverless.

El enfoque moderno: Direct VPC Egress

Direct VPC egress es la solución nativa. En lugar de enrutar el tráfico a través de un puente de VMs, Cloud Run inyecta directamente interfaces de red (ENIs) de tu VPC en el entorno donde se ejecutan tus contenedores.

Tu servicio obtiene IPs directamente de una subred de tu VPC. El tráfico fluye sin intermediarios. Es más rápido, más elegante y, sobre todo, no hay VMs puente que aprovisionar, monitorear o pagar. El ancho de banda ya no está limitado por el tipo de máquina de un conector; Cloud Run soporta un throughput de hasta 1 Gbps por cada instancia de contenedor individual.

Manos a la obra

Si estás empezando un proyecto nuevo, Direct VPC egress debería ser tu configuración predeterminada. Veamos cómo configurarlo usando la CLI de Google Cloud (gcloud).

Implementando Direct VPC Egress

Para conectar un servicio de Cloud Run directamente a tu VPC, usas la bandera --vpc-egress junto con tu red y subred.

gcloud run deploy SERVICE_NAME \
    --image=REGION-docker.pkg.dev/PROJECT_ID/REPO_NAME/IMAGE:TAG \
    --network=NETWORK \
    --subnet=SUBNET \
    --vpc-egress=private-ranges-only \
    --region=REGION

El parámetro --vpc-egress=private-ranges-only le dice a Cloud Run que envíe solo el tráfico dirigido a IPs privadas (como RFC 1918) a través de la VPC. Si usas all-traffic, todo el tráfico de salida pasará por tu VPC, lo cual es útil si quieres forzar la salida a internet a través de un Cloud NAT en tu red para tener una IP estática de salida.

Qué pasa si aún necesitas el Connector

Si por alguna razón (que veremos más adelante) necesitas seguir usando el Serverless VPC Access connector, primero debes crearlo:

gcloud compute networks vpc-access connectors create CONNECTOR_NAME \
    --network=NETWORK \
    --region=REGION \
    --range=10.8.0.0/28

Y luego asociarlo a tu despliegue:

gcloud run deploy SERVICE_NAME \
    --image=REGION-docker.pkg.dev/PROJECT_ID/REPO_NAME/IMAGE:TAG \
    --vpc-connector=CONNECTOR_NAME \
    --region=REGION

Costos, límites y errores comunes

Aquí es donde la teoría choca con la realidad del presupuesto y la operación.

Costos

  • Direct VPC egress: ¡Es gratis! No pagas por el enlace en sí, solo por el tráfico de salida estándar (egress) que genere tu aplicación hacia otras zonas o hacia internet, igual que con cualquier otro recurso de GCP.
  • Serverless VPC Access connector: Pagas por las instancias de Compute Engine que forman el conector, 24/7. Un conector f1-micro (mínimo 2 instancias) te costará unos pocos dólares al mes, pero un conector de alto rendimiento con varias instancias e2-standard-4 engordará tu factura significativamente, lo uses o no. (Precios al 2026-10-30).

Límites de IP y Escalamiento

El error más común con Direct VPC egress es quedarse sin direcciones IP. Por cada instancia de contenedor, Cloud Run consume direcciones IP de tu subred. Además, retiene estas IPs por un tiempo durante los escalados hacia abajo (hasta 20 minutos para servicios, y 7 minutos después de terminar para jobs). La documentación oficial recomienda que el rango de tu subred sea /26 o más grande. Si tu subred se queda sin IPs, tus servicios no podrán escalar y los nuevos despliegues fallarán con un error de insufficient free IP addresses.

Rendimiento de Arranque

Direct VPC egress puede añadir latencia durante el arranque en frío (cold start). La documentación señala que puedes experimentar demoras de un minuto o más al establecer conexiones durante el inicio de la instancia. Se recomienda encarecidamente usar un HTTP startup probe que verifique la conectividad antes de aceptar peticiones.

Cuándo NO usar Direct VPC egress

Aunque Direct VPC egress es superior en casi todos los aspectos, no es una bala de plata. Hay escenarios donde el viejo conector sigue siendo el capitán del barco:

  1. Si usas Cloud NAT agresivamente: La documentación oficial de Google indica explícitamente que, si usas Cloud NAT, Direct VPC egress puede causar demoras de arranque en frío de 30 segundos o más. En estos casos, para un mejor rendimiento de arranque, se recomienda usar el Serverless VPC Access connector.
  2. Limitaciones de cuota severas: Existe una cuota de uso de Cloud Run que limita el número máximo de instancias de contenedor que puedes configurar con Direct VPC egress. Si superas esta cuota y no puedes pedir un aumento inmediato, el conector es tu plan B.
  3. Falta de soporte de red (Shared VPC): Asegúrate de que las políticas de tu organización y tu topología de Shared VPC soporten el modelo de Direct VPC egress antes de hacer el cambio, aunque hoy en día el soporte es casi universal.

Llévatelo

Si estás configurando la red para tu aplicación Cloud Run hoy, quédate con esto:

  • Por defecto, usa Direct VPC egress: Es más barato, escala mejor y no requiere administrar máquinas virtuales puente. Configúralo con --vpc-egress.
  • Prepara tus subredes: Asigna un bloque CIDR amplio (al menos /26) a la subred que uses para Cloud Run con Direct VPC, porque el escalamiento y la retención de IPs son glotones.
  • Monitorea los arranques en frío: Si conectas Cloud Run a Cloud NAT usando Direct VPC y notas que los arranques en frío se disparan por encima de los 30 segundos, considera volver al Serverless VPC Access connector para esa carga de trabajo específica.
