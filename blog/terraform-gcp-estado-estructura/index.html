Terraform en GCP: Estado Remoto y Estructura Sana

Tu proyecto de Terraform se vuelve inmanejable por el estado local y mala estructura. Descubre cómo configurar un backend remoto en GCS y organizar módulos.

Empiezas un proyecto con Terraform. Todo va de maravilla. Despliegas una instancia de Compute Engine, luego una red VPC, y te sientes el dueño del universo.

El archivo main.tf tiene cien líneas, manejables. Trabajas solo en tu máquina, con un humilde archivo terraform.tfstate local. Eres ágil y productivo.

Pero luego, tu equipo crece. Entra tu colega, clona el repositorio, añade una base de datos de Cloud SQL y ejecuta terraform apply. De pronto, sus cambios colisionan con los tuyos. Recursos duplicados, configuraciones pisadas, caos total en producción.

El problema es claro: Terraform no sabe qué hizo la otra persona.

Si Terraform es el mapa de tu infraestructura, el archivo de estado (tfstate) es la brújula que indica dónde estás parado exactamente. Y si cada miembro del equipo tiene una brújula distinta, el naufragio está garantizado.

El problema real

El archivo terraform.tfstate mapea tu configuración escrita en HCL (HashiCorp Configuration Language) con los recursos reales aprovisionados en Google Cloud. Por defecto, Terraform crea este archivo de estado de forma local, en la carpeta donde ejecutas los comandos.

Esto funciona perfectamente bien para un proyecto personal o una prueba de concepto en tu propia terminal. Pero cuando múltiples ingenieros interactúan con la misma infraestructura a través del mismo código, usar un estado local desencadena una tormenta perfecta.

Si dos personas ejecutan un terraform apply al mismo tiempo, el estado local no tiene forma de arbitrar la concurrencia. No existe un mecanismo de bloqueo (lock). Terraform intentará crear o modificar recursos simultáneamente, lo que puede corromper el estado y resultar en recursos huérfanos o inconsistentes.

Por otro lado, está el problema de la estructura. A medida que un proyecto crece, un único archivo main.tf monolítico se vuelve inmanejable. Si metes toda la configuración de red, bases de datos y microservicios en el mismo archivo, cualquier mínimo cambio requerirá evaluar el estado de todo el proyecto, volviendo las ejecuciones lentas y peligrosas.

La solución oficial y robusta de Google Cloud a estos dos problemas pasa por configurar un “backend” remoto en Cloud Storage (GCS) y estructurar el código en módulos reutilizables. Esto permite que el estado sea compartido y protegido, mientras el código se mantiene ordenado y predecible.

Cómo funciona

Cuando configuras un backend remoto en Cloud Storage, Terraform deja de escribir el archivo tfstate en tu disco local. En su lugar, lee y escribe este archivo directamente en un bucket de GCS.

El componente vital de este flujo es el bloqueo de estado (state locking). Cuando ejecutas una operación que podría modificar el estado, como un apply, Terraform automáticamente bloquea el archivo en Cloud Storage.

Si tu colega intenta ejecutar otro comando de modificación en ese exacto instante, Terraform detectará que existe un bloqueo activo y le pedirá que espere. Esto garantiza que las operaciones se procesen de una en una, preservando la integridad de tu infraestructura.

Además del estado remoto, la estructura recomendada implica dividir el proyecto. En lugar de un gran directorio, debes separar los recursos por ambientes (como desarrollo y producción) y abstraer los patrones comunes en módulos reutilizables. Un módulo es simplemente una carpeta con archivos de Terraform, que agrupa recursos lógicos. Por ejemplo, en lugar de declarar quince recursos individuales para crear un clúster de Kubernetes seguro, abstraes todo eso en un módulo “gke_cluster”.

Manos a la obra

Vamos a configurar un backend remoto robusto en Google Cloud. Necesitamos aprovisionar un bucket de GCS que cumpla con los estándares de seguridad para almacenar información tan sensible.

Primero, créate un archivo temporal llamado bootstrap.tf solo para crear el bucket. Asegúrate de tener permisos administrativos (o al menos roles/storage.admin).

// Archivo: bootstrap.tf
resource "google_storage_bucket" "terraform_state" {
  name     = "PROJECT_ID-tfstate"
  location = "US"

  force_destroy               = false
  public_access_prevention    = "enforced"
  uniform_bucket_level_access = true

  versioning {
    enabled = true
  }
}

Fíjate en tres detalles clave de este bucket. force_destroy está en falso para evitar que borremos el bucket por accidente si tiene objetos dentro. Activamos public_access_prevention porque el estado de Terraform suele contener secretos y contraseñas en texto plano. Y lo más crucial, habilitamos el versioning.

Inicializa y aplica esta configuración inicial:

terraform init
terraform apply

Una vez que el bucket existe, debemos decirle a Terraform que lo utilice. En tu archivo principal (normalmente llamado backend.tf por convención), añade el bloque de configuración del backend:

// Archivo: backend.tf
terraform {
  backend "gcs" {
    bucket = "PROJECT_ID-tfstate"
    prefix = "terraform/state"
  }
}

El parámetro prefix sirve para organizar mejor el bucket, permitiendo almacenar el estado de distintos proyectos o ambientes bajo diferentes rutas. Ahora, ejecuta la migración:

terraform init -migrate-state

Terraform detectará que estás moviendo el estado local al remoto y te pedirá confirmación. Una vez hecho esto, puedes borrar tu archivo terraform.tfstate local con total seguridad.

Para organizar el código y aplicar buenas prácticas de estilo, la documentación de Google Cloud sugiere dividir el proyecto de la siguiente manera. Crea agrupaciones lógicas para tus archivos en el directorio raíz (por ejemplo: network.tf, instances.tf, variables.tf, outputs.tf).

Si usas módulos, asegúrate de mantenerlos en una estructura estándar. Cada módulo debe tener su propio main.tf, variables.tf y su documentación descriptiva. Usa guiones bajos para nombrar recursos, mantén los nombres en singular y no repitas el tipo de recurso en el nombre.

// Recomendado:
resource "google_compute_instance" "web_server" {
  name = "web-server"
}

// No recomendado:
resource "google_compute_instance" "web-server" {
  name = "web-server"
}

Costos, límites y errores comunes

Almacenar tu estado en Cloud Storage incurre en los costos estándar del servicio, principalmente por almacenamiento y operaciones de lectura/escritura.

Dado que el archivo de estado suele ser pequeño (desde unos pocos kilobytes a un par de megabytes), el almacenamiento es casi gratuito. Sin embargo, hay un detalle a considerar: el versionamiento de objetos.

Tener el versionamiento activado es fundamental. Si alguien corrompe el estado por error, podrás restaurar una versión anterior desde el bucket. Pero cada vez que ejecutas Terraform, se crea una nueva versión completa del archivo. Con miles de ejecuciones al mes en proyectos grandes, esto se acumula.

Al 9 de noviembre de 2026, el almacenamiento estándar en GCS en la multirregión de EE. UU. ronda los 0.026 USD por GB al mes. El costo por versionamiento es minúsculo en proyectos pequeños, pero como buena práctica de limpieza, considera configurar una regla de ciclo de vida (Object Lifecycle Management) en el bucket para eliminar automáticamente versiones de estado con más de noventa días de antigüedad.

Un error muy común es olvidar que el estado de Terraform puede incluir secretos en texto plano, como contraseñas generadas o tokens de bases de datos. Configurar correctamente los controles de acceso IAM sobre el bucket es imperativo. Solo los administradores de infraestructura y las cuentas de servicio autorizadas por los pipelines de CI/CD deben tener el permiso roles/storage.objectAdmin en el bucket del estado. Los desarrolladores estándar solo deberían necesitar permisos de lectura, si acaso los necesitan de manera directa.

Cuándo NO usarlo

El backend en Cloud Storage es el estándar de facto para Google Cloud, pero no es absoluto.

Si estás utilizando Terraform Cloud o Terraform Enterprise para gestionar tus ejecuciones, deberías usar su propio backend integrado. Terraform Cloud ya gestiona el estado, el bloqueo, el versionamiento y la concurrencia de forma nativa e invisible. En ese caso, configurar manualmente un bucket de GCS es redundante y solo añade complejidad operativa.

Tampoco necesitas apresurarte a usar un estado remoto si estás aprendiendo la herramienta, probando un tutorial de cinco minutos o validando la sintaxis localmente antes de desechar todo el entorno de pruebas. Para casos de aprendizaje descartable, el estado local sigue siendo la vía rápida e indolora.

Llévatelo

  • Protege tu estado. Configura un bucket GCS con versionamiento, prevención de acceso público y controles estrictos de IAM para guardar de forma remota y segura tu archivo tfstate.
  • Estructura por función. Divide tus configuraciones largas en archivos descriptivos como network.tf o en módulos dedicados, evitando el monolito inmanejable.
  • Limpia el historial. Usa las reglas de ciclo de vida de Cloud Storage para borrar versiones antiguas de tu estado remoto, controlando así los costos ocultos a largo plazo.
